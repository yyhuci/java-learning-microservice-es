## 一、Nacos：服务注册与配置中心

### 已完成

- 启动 Nacos 3.0.3 单机版，控制台因 `8080` 被占用改用 `8081`，Nacos 服务端口仍为 `8848`。
- `shop-user` 和 `shop-order` 都成功注册到 Nacos 的 `DEFAULT_GROUP`。
- 为 `shop-user` 创建 Nacos 配置：`shop-user.yaml`，组为 `DEFAULT_GROUP`。
- `shop-user` 通过 `spring.config.import` 读取 Nacos 配置；服务端口由 Nacos 配置为 `8053`。

### 核心理解

- **服务注册**：服务启动时把自己的服务名和地址登记到 Nacos。
- **服务发现**：调用方按服务名从 Nacos 获取可用实例，而不是把 IP 和端口写死在代码里。
- **配置中心**：把端口、开关等可变配置放到 Nacos，应用启动时读取。
- `DEFAULT_GROUP` 是 Nacos 的默认分组，用于给服务或配置分类；生产环境可按业务、环境或团队拆分分组。

## 二、OpenFeign 与 LoadBalancer：服务间调用

### 已完成

- 父工程统一管理 Spring Cloud `2025.0.0` 和 Spring Cloud Alibaba `2025.0.0.0` 的依赖版本。
- `shop-common` 引入 OpenFeign 和 Spring Cloud LoadBalancer，并放置公共 Feign 契约。
- 定义 `UserServiceFeign`：通过服务名 `shop-user` 调用 `GET /users/hello`。
- `shop-order` 使用 `@EnableFeignClients(basePackages = "com.tjetc.openfeign")` 扫描 Feign 客户端。
- `OrderController` 注入 Feign 接口，并暴露 `GET /orders/user-hello`。
- 实际验证：访问 `http://localhost:8052/orders/user-hello`，成功得到用户服务返回的数据。

### 核心理解

- `DiscoveryClient + RestTemplate` 是较早期的组合：先向注册中心查询实例，再自行拼接地址发 HTTP 请求。
- **OpenFeign** 把这两个步骤封装成接口调用；调用 `userServiceFeign.hello()` 时，会按服务名发现实例并发送请求。
- **LoadBalancer** 在服务存在多个实例时选择其中一个实例，实现客户端负载均衡。
- `@FeignClient` 标注在接口上，因此 Feign 使用接口声明“调用哪个服务、哪个接口”；运行时由 Spring 生成代理对象。
- 公共 Feign 接口放到 `shop-common` 的目的是让调用契约可复用，业务模块只依赖公共模块，不反向依赖具体服务。

## 三、Sentinel：服务容错与流量控制

### 控制台与项目接入

- 启动 Sentinel Dashboard 1.8.9；默认 `8080` 被占用，因此使用 `8858`。
- `shop-order` 引入 `spring-cloud-starter-alibaba-sentinel`。
- 在 `application.yml` 配置 Sentinel 控制台地址 `127.0.0.1:8858` 和客户端通信端口 `8719`。
- 访问订单接口后，Sentinel 控制台成功发现应用 `shop-order` 并显示资源链路。

### 已验证的流控模式

- **直接模式**：为 `/orders/user-hello` 配置 QPS 阈值 `3`。快速连续访问时，超过阈值的请求返回 `Blocked by Sentinel (flow limiting)`。
- **关联模式**：为 `/orders/message1` 设置关联资源 `/orders/message2`。连续压测 `message2` 后，访问 `message1` 被限流，验证了“以非核心接口让步保护关键接口”的思路。
- **链路模式**：
  - 新建 `OrderService` 接口和 `OrderServiceImpl` 实现层。
  - 使用 `@SentinelResource("orderServiceMessage")` 标记公共 Service 方法。
  - `/orders/message1` 和 `/orders/message2` 都调用该方法。
  - 配置 `spring.cloud.sentinel.web-context-unify: false`，让 Sentinel 保留不同 URL 的独立调用上下文。
  - 为 `orderServiceMessage` 配置链路规则，只限制从 `/orders/message1` 进入的调用。
  - 压测结果：`message2` 连续请求均为 `200`；`message1` 第一次为 `200`，后续为 `500`。这里的 `500` 是当前未设置 `blockHandler` 时 Sentinel 抛出限流异常的预期现象。

### 已验证的流控效果

- **快速失败**：超过阈值立即返回 `429`。
- **Warm Up**：配置 QPS `3`、预热 `10` 秒，理解服务冷启动时先用较低吞吐量承接流量的目的。简单本地突发请求不适合作为观察预热曲线的唯一依据。
- **排队等待**：配置 QPS `3`、最大等待 `5000ms`。10 个并发请求全部返回 `200`，耗时约按 `0.33` 秒递增，最后一个约 `2.93` 秒完成，验证请求被匀速排队而不是直接拒绝。

### 核心理解

- Sentinel 从流量、异常和系统负载等角度保护服务稳定性。
- **QPS** 是每秒通过的请求数；`429` 表示请求被限流。
- **关联限流**关注另一个资源的流量；**链路限流**关注同一资源从哪个上游接口进入，粒度更细。
- `web-context-unify: false` 的作用是不合并 Web 接口入口，使 Sentinel 能看到：

```text
/orders/message1 -> orderServiceMessage
/orders/message2 -> orderServiceMessage
```

- `OrderService` 是接口层，规定业务能力；`OrderServiceImpl` 是实现层，写具体逻辑并由 `@Service` 注册为 Spring Bean。
